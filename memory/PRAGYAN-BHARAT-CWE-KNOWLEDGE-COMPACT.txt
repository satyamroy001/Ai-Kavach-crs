PRAGYAN-BHARAT LLM SECURITY KNOWLEDGE BASE
VERSION: compact+examples
PURPOSE: retrieval context for small code-security LLMs (especially 1B-3B).
CORE RULE: CWE label alone is NEVER evidence.

MANDATORY REASONING:
1. Locate the exact operation.
2. Identify the security property being violated.
3. Trace the relevant data/control/lifetime path.
4. Prove the condition is reachable from the supplied code.
5. Distinguish a real vulnerability from a coding smell or theoretical possibility.
6. Select the most specific CWE supported by evidence.
7. If the evidence is insufficient, output NONE / FALSE POSITIVE.
8. For a proposed fix, preserve behavior and ownership; do not merely silence a symptom.

CONCURRENCY RULE:
A mutex around one access is not automatically a lifetime fix. Prove:
thread creation -> shared object ownership -> possible free/destroy -> worker dereference.
A pointer becoming NULL does not repair another thread's stale pointer.
A lock protects only code that actually acquires the same lock.

MEMORY-LIFETIME RULE:
Track:
ALLOCATE -> OWNER -> TRANSFER/COPY -> ASYNC USE -> FREE/DESTROY -> JOIN/QUIESCE.
If a worker can dereference after free, classify the lifetime bug even if the dereference is inside a mutex.

ALLOCATION-SIZE RULE:
strlen(s) bytes is not enough for a C string; storage for the terminating '\0' is required.
Do not use sizeof(pointer) as the size of the pointed-to allocation.

RAG USAGE:
Treat the retrieved CWE entry as a hypothesis/checklist, not proof.
Never invent a vulnerability merely because the CWE name resembles an API or pattern.
Prefer exact source evidence over generic CWE prose.
